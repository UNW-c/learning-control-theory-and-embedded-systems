该部分主要是学习嵌入式开发中的通信相关内容，目前涉及 MQTT、IPC、TCP、UDP 和 socket。

## MQTT

MQTT 的全称是 Message Queuing Telemetry Transport，是一个基于 pub/sub 的轻量级消息协议，跑在 TCP 上，默认端口 1883，用在设备上报状态、远程下发控制这类场合。报文头最小只有两个字节，剩下的都是载荷。

关于它，我认为本质和单片机上进程间通信用的 IPC、以及 ROS 里那套 pub/sub 模式，内核是一样的。都是发布者只管发布，订阅者只管订阅，两边不直接建立联系。发布的时候不指定接收方，订阅的时候也不指定发送方；MQTT 和 ROS 靠 topic 这个字符串对上，发到同一个 topic 的报文，订了这个 topic 的客户端都能收到；板子上的队列没有 topic 这一层，发送和接收拿的是同一个 `QueueHandle_t`。

这样发布方和订阅方之间就解耦了，任何一个订阅端怎么改，都影响不到发布方。

MQTT 只管把报文往 topic 上送，载荷里放什么由两边自己约定，结构体、JSON、protobuf 都行。

## 关于 pub/sub

pub/sub 是发布者、订阅者和一层中间件：发布者把消息发到某个 topic 上，不指定接收方；订阅者声明自己订阅哪个 topic，中间件把这条订阅关系存进订阅表；之后每来一条消息，中间件按 topic 查出订阅它的订阅者，逐个投过去，一人一份。发布者按自己的节奏继续发，订阅者随时可以订阅和退订，两边都不用改对方的代码。

这套结构在 MQTT、ROS 和板子的队列上都有，差别在 topic 是什么、订阅关系存在哪里。

MQTT 的 topic 是字符串，订阅关系存在 broker 的订阅表里，broker 按 `/` 分层匹配，一条消息可以投给多个客户端。ROS 的 topic 也是字符串，订阅关系存在 master 上，消息带 `.msg` 类型，类型对不上会直接报错，节点之间按 topic 建连接。板子上的队列没有 topic，发送和接收拿到的是同一个 `QueueHandle_t`，订阅关系在写代码的时候就定了，所以队列只能一对一，一条消息只有一个任务取得到。

另一个差别是发布者和订阅者要不要同时在场。队列的数据放在内核缓冲里，发送方发完就走，接收方晚一点来取也行，取走就没了；MQTT 里由 broker 存下来，QoS 1/2 加上会话，掉线再上来还能补；ROS 是节点之间直接建连接，订阅者不在线，那条消息就丢了。

## 关于 IPC

IPC 是进程间通信，操作系统提供的一套让进程交换数据的机制。单片机上一般说任务间通信，跑的是 RTOS 的几个任务，要做的事一样：一个任务产生数据，另一个任务要用，中间得有东西把数据递过去。

板子上常见的有这么几种：

- 队列，单向传数据，发送方塞一条，接收方取一条，用得最多
- 信号量，不传数据，只表示现在有几份资源，用来同步或者计数
- 互斥量，保证一段代码同一时刻只有一个任务进去
- 事件标志，一个 bit 表示某件事发生了，几个任务可以一起等

Linux 上换成管道、消息队列、共享内存和 Unix socket，差别在拷贝次数、有没有消息边界、能不能跨机器。板子上用得最多的是队列，它是一块环形缓冲，建的时候给定深度和单条消息的大小。

```c
QueueHandle_t q = xQueueCreate(8, sizeof(chassis_msg_t));

/* 读传感器的任务 */
chassis_msg_t msg = { .vx = vx, .wz = wz };
xQueueSend(q, &msg, 0);

/* 算控制的任务 */
if (xQueueReceive(q, &msg, pdMS_TO_TICKS(2)) == pdTRUE) {
    /* 这一拍的速度给定量 */
}
```

队列那块内存是建队列的时候从堆上划出来的，`xQueueSend` 把结构体整个按值拷进去，取的时候再拷出来，所以单条消息不能做得太大，传指针又要自己管那块内存什么时候释放、什么时候能改。第三个参数是等待时间，填 0 表示队列满的时候直接返回失败，也可以填一个超时，等别人取走一条腾出位置。

队列满了怎么处理，实际上是个取舍。姿态这种数据丢一条无所谓，下一拍还有新的，丢掉比把发送方堵在这儿强；状态变化这种一条都不能少的，就得等，或者把队列开大一点，再不行就把发送方自己的频率降下来。

接收这一边一般是挂在 `xQueueReceive` 上阻塞着的，有数据了就被调度起来，没有数据就让出 CPU。发送方在自己的 `while` 里按时发，接收方在自己的 `while` 里按时取，两边的节奏互不影响。中断里也可以往里塞，用的是带 `FromISR` 后缀的版本，中断上下文里不能调普通的发送接口。

中断是外设或者定时器发出的中断请求，CPU 停下当前正在执行的指令，跳到中断服务函数里去。数据进队列以后，内核把阻塞在 `xQueueReceive` 上的任务从阻塞挪到就绪，和中断的结果一样，都是事件到了才处理。区别在于中断里不能阻塞、不能等锁、栈也小，所以中断服务函数里只能做最少的事，清个标志、把数据搬到缓冲里、往队列里塞一条，剩下的交给任务。串口一帧数据收了一半，剩下的半帧什么时候来是不确定的，在中断里等是等不起的。

关于 IPC 的实际应用，可以看湖南大学跃鹿战队开源的那套电控框架。整车的数据就是靠这一类机制转起来的：云台、底盘、发射几个任务各跑各的周期，谁也不能停下来等谁，中间靠 module 层的一个消息中心。抽象出来是这样，一个任务把自己产生的数据挂到一个话题上，需要这份数据的任务订阅这个话题，消息中心按话题把数据分发给每个订阅者，一人一份。

取数据是订阅方主动去拿的，自己那一份空了就说明这拍没有新数据，接着干别的事。每份只留最新的一条，控制类的数据要的就是最新那一拍，旧的留着也用不上。

和直接用队列的区别在这：队列一条消息只能给一个任务取走，要发给三个任务就得建三个队列自己挨个发；消息中心推一次就行，底下几个人订就拷几份，拷贝是它做的。
