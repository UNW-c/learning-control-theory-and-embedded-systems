## TCP

TCP 是传输控制协议，面向连接、可靠、有顺序，两端在传数据之前先建立连接，中间丢了会重传，上层收到的字节流顺序和发出去的一致。它是通用协议，正常情况下和嵌入式没多大关系，PC 上写上位机天天在用，跟板子本身没什么绑定。

但边缘设备要联网就绕不开它，它在嵌入式里有两个用处。一个是 MQTT 的底座，MQTT 的报文跑在 TCP 上，设备要上报就得维持这条连接；另一个是自己直接连，上位机调参、板子和板子之间、板子和网关之间，两边都没有现成的协议可用，得自己定一个。

### 三次握手

三次握手是建立连接时交换的三个报文，客户端发 SYN，服务端回 SYN+ACK，客户端再回 ACK。

```
客户端                                服务端
  | ---- SYN  seq=x --------------->  |
  | <--- SYN+ACK  seq=y ack=x+1 ----  |
  | ---- ACK  ack=y+1 ------------->  |
```

三个报文下来，客户端确认了自己的发送和服务端的接收都正常，服务端也确认了客户端的发送和自己的接收都正常，两边的序号在这个过程里对齐。服务端把 SYN 和 ACK 合成一个报文，所以是三次而不是四次。

网络里可能还飘着上一次连接留下的 SYN，客户端收到第三次的 SYN+ACK 才认为连接建好，晚到的旧 SYN 最多在服务端留一个半连接，不会让两端带着不同的序号开始传数据，这是错位保护的那一层。

### 四次挥手

四次挥手是断开连接时交换的四个报文。TCP 是全双工的，两个方向各关一次，客户端发 FIN 表示自己这边不发数据了，服务端回 ACK，但它可能还有数据没发完，等发完再发自己的 FIN，客户端回 ACK。因为 ACK 和 FIN 中间可能隔着数据，所以是四次。

```
客户端                                服务端
  | ---- FIN ---------------------->  |
  | <--- ACK -----------------------  |
  | <--- FIN -----------------------  |
  | ---- ACK ---------------------->  |
```

主动关闭的一方会进入 TIME_WAIT，等 2MSL，Linux 上是 60 秒。这段时间里如果最后的 ACK 丢了，对方重发 FIN 过来还能收到并且回一个；连接残留在网络里的报文也有时间散掉，新连接不会收到旧连接的数据。短连接开关频繁的时候端口会被这个状态占住，bind 报 EADDRINUSE，一般是改成一条长连接，或者设 SO_REUSEADDR。

### 自定义协议

直接用 TCP 通信的时候，协议要自己写。TCP 给的是字节流，没有消息边界，发两次 100 字节，对面可能一次收到 60、下一次收到 140，也可能两次粘在一起一次收到 200，所以数据要一帧一帧地定。

帧一般这么定：

- 帧头，两个字节，比如 `0xAA 0x55`，用来在字节流里找一帧的开始
- 长度，两个字节小端，表示这一帧还剩多少字节
- 命令字，一个字节，区分这一帧是做什么的，`0x01` 设速度，`0x02` 读状态
- 载荷，一般是定长的结构体，命令字种类多、长度差得远的时候才带长度字段变长
- 校验，CRC-16/MODBUS 或者累加和
- 帧尾，`0x0D 0x0A`，兜底

```
AA 55 | 0C 00 | 01 | 3F 80 00 00 40 00 00 00 ... | CRC_L CRC_H | 0D 0A
 帧头   长度2   命令      载荷 12 字节                 校验2       帧尾
```

CRC 算从帧头到载荷末尾，不含它自己：

```c
static uint16_t crc16_modbus(const uint8_t *buf, int len)
{
    uint16_t crc = 0xFFFF;
    while (len--) {
        crc ^= *buf++;
        for (int i = 0; i < 8; i++)
            crc = (crc & 1) ? (crc >> 1) ^ 0xA001 : (crc >> 1);
    }
    return crc;                     /* 发送时低字节在前 */
}
```

帧之外还要发心跳，隔固定时间发一个空载荷的帧，连续几个周期收不到任何帧就当断线，关掉重连。

### 粘包

收的一侧要有缓冲，边收边切。一次 recv 返回的是这次收到多少字节，可能是半帧、一帧，也可能是两帧粘在一起。

```c
/* buf 里是还没处理完的字节，len 是有效长度 */
static int frame_parse(const uint8_t *buf, int len)
{
    for (int i = 0; i + 9 <= len; i++) {
        if (buf[i] != 0xAA || buf[i + 1] != 0x55)
            continue;                                  /* 不是帧头，往后找 */
        int payload = buf[i + 2] | (buf[i + 3] << 8);
        int total   = 2 + 2 + 1 + payload + 2 + 2;     /* 头 长 命令 载荷 CRC 尾 */
        if (i + total > len)
            return 0;                                  /* 半包，等下次收 */
        if (!crc16_check(buf + i, total - 4))          /* 帧头算到载荷末尾 */
            continue;
        if (buf[i + total - 2] != 0x0D || buf[i + total - 1] != 0x0A)
            continue;
        handle_frame(buf + i, total);
        return total;
    }
    return 0;
}
```

处理完一帧要把剩下的字节往前挪，再在里面接着找；校验不过的帧丢掉，从下一个字节重新找帧头；长度字段要设上限，出现乱码的时候长度可能被读成一个很大的数，不加限制会一直等后续数据，再也对不齐；半包的时候保留已经收到的字节，等下一次 recv 补上。
